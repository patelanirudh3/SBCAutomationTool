## Reporting Issues Identified

### Missing / mismatched GUI metrics

The GUI initially showed some incorrect values:

- `Total INVITEs Sent` showed `0`.
- `Total Acknowledged` showed `0` or a lower-bound value.
- `Extensions currently in call` showed call count instead of extension count.
- `Concurrent Calls` showed `20 / 30`, which looked like under-capacity even though the 41-extension pool could only support 20 concurrent calls.

### Single-pool capacity clarification

The system uses one pool of user agents. Each active call consumes two extensions:

```text
1 active call = 2 extensions in use
```

So with 41 registered/subscribed extensions:

```text
max concurrent calls = floor(41 / 2) = 20
extensions in use at full capacity = 40
idle extensions at full capacity = 1
```

This means showing `1` idle extension during a 20-call steady state is correct.

### Extensions in use

The correct source for extensions currently allocated to calls is `non_idle_count`, not `established_count`.

Reason:

- `non_idle_count` includes extensions allocated to call setup and established call phases.
- `established_count` would miss calls that are still in setup, for example when `INVITE` was sent but `ACK` has not yet been received.

Desired live display:

```text
Idle Extensions       = idle_count
Extensions In Use     = non_idle_count
Reg-only Extensions   = reg_only_count
Concurrent Calls      = concurrent_calls
```

## Counter Semantics Agreed

The call-reporting counters should be session-level and milestone-driven.

Desired definitions:

```text
No Response INVITEs = INVITEs sent but no 100 Trying received
Attempted           = outbound initial INVITE received 100 Trying
Answered            = UAC received 200 OK for INVITE
Acknowledged        = UAS received ACK
Completed           = UAC received 200 OK for BYE
Failed              = explicit failure/timeout/final failure only
```

Important rule:

```text
Failed must not be calculated as Attempted - Completed during live traffic.
```

That formula is misleading during hold time because many calls are legitimately in progress.

Correct live relationship:

```text
INVITEs Sent >= Attempted >= Answered >= Acknowledged >= Completed
```

During normal healthy traffic, because signaling is fast:

```text
Attempted ~= Answered ~= Acknowledged
Acknowledged > Completed
```

The hold timer creates the gap between `Acknowledged` and `Completed`, not usually between `Attempted`, `Answered`, and `Acknowledged`.

## ASR and CSR Design

It was agreed to show both ASR and CSR.

### ASR

```text
ASR = Answer Seizure Ratio
ASR = Answered / Attempted * 100
```

Meaning:

- Measures whether accepted INVITEs reached `200 OK` for INVITE.
- Does not wait for hold time or BYE completion.
- Should become healthy quickly when the call answer path works.

### CSR

```text
CSR = Call Success Ratio
CSR = Completed / Attempted * 100
```

Meaning:

- Measures full call lifecycle success.
- Requires `INVITE / 200 / ACK`, media hold, `BYE / 200`.
- Can lag ASR during active traffic because calls are still in hold.

Backend-calculated ASR/CSR was preferred so that the GUI, JSON report, summary logs, and live metrics all use one source of truth.

## Timer / Drain Behavior

A major issue was found in timed traffic mode.

Observed problem:

- When the traffic duration expired, active calls were interrupted.
- Many calls failed with `bye_200 timeout` even though `200 BYE` responses arrived milliseconds later.

Desired behavior:

```text
When traffic timer expires:
1. Stop sending new INVITEs.
2. Do not cancel in-flight call contexts.
3. Let active calls finish:
   INVITE -> 200 OK -> ACK -> RTP/hold -> BYE -> 200 OK
4. Then transition to cleanup-ready/final reporting.
```

After adjustment, a later run showed the timer boundary was handled better:

- No mass `bye_200 timeout` at the traffic deadline.
- In-flight calls continued to receive `BYE_200`.
- Traffic moved to cleanup-ready only after active calls drained.

## 100/407 Race and Dialog Queue Design

Two failed calls were traced to a race where `100 Trying` and `407_INVITE` arrived back-to-back.

Observed pattern:

```text
INVITE_SENT
100 Trying classified
407_INVITE classified
TRYING_100 logged
No AUTH_407 logged
CALL_TIMEOUT
200_CANCEL buffered
```

Root cause:

- The old event wait model used short-lived event-code channels.
- A second event could be lost or orphaned if it arrived immediately after the first event woke the waiter.

Design direction agreed:

```text
Phase 1: Harden old event-code path for non-call flows.
Phase 2: Use durable per-dialog queues for call traffic.
```

Non-call flows remain on the hardened old path:

```text
REGISTER
SUBSCRIBE
UNREGISTER
UNSUBSCRIBE
NOTIFY handling
```

Call traffic uses per-dialog durable queues:

```text
INVITE
100
407_INVITE
180/183
200_INVITE
ACK
BYE
200_BYE
```

Important design guarantee:

- This change affects receive-side event routing only.
- INVITEs still use the same `ExtensionAgent`, same persistent SIP socket, same local host/port, and same Contact/Via construction as REGISTER.

## Live Progress Report Layout Design

The live report was redesigned conceptually into four sections:

```text
Top:      Call funnel + ASR/CSR
Middle:   Concurrent calls / pool usage
Runtime:  CPS, Avg PDD, Avg Hold, Sockets
Charts:   Trend / history
```

### Top panel

The top panel should show call-flow funnel counters in one structured area:

```text
No Response       Attempted Call     Answered Call      Acknowledged Call   Completed Call    Failed Call
(INV/no 100)      (INV/100)          (INV/.../200)      (INV/.../ACK)       (BYE/200)         (explicit fail)
```

ASR and CSR should appear below the funnel counters in the same top card, using progress bars:

```text
ASR = Answered / Attempted
CSR = Completed / Attempted
```

The separate side-by-side ASR/CSR card caused overlap on some screen sizes, so the safer design is to keep ASR/CSR inside the top card below the funnel counters.

### Runtime signals

The old `traffic-local` card duplicated many values already shown in the upper progress area.

The remaining useful runtime-only values are:

```text
Actual CPS
Avg PDD
Avg Hold
Sockets
```

The CPS progress bar is not needed; only the value is required.
